All of us have been there: You are working with old technology and although you know there is a way better solution to handle your business case, you can't change the technology. There's simply no point in rewriting everything to just move to a better approach.

In my case, I was working in an agency for a client that had a classical CMS that generated full HTML pages and embedded Vue components that were rendered on the client.
My agency provided those vue components while the client was using the CMS to manage their website. We ran into a problem where the website grew and grew and the client side rendering became increasingly slow, ran into a lot of layout shifts and many http requests that browser needed to make after rendering the whole website, because rendered components demanded additional data from the server.
Server Side Rendering would have solved a lot of these problems: Layout shifts will be eliminated due to the html already being rendered. Resources can be immediately preloaded and preload meta tags can be generated by SSR. And of course especially mobile devices would benefit from the reduced client side work.
But as you know, we can't have that because we would require a nodejs server and also a vue template that is fixed and can be precompiled by vue.
Although I couldn't find anyone how would try to still solve this problem without rewriting the whole project, I found a pretty simple solution that I want to explain here.

## The approach
You can view the code on my github repository [here](https://github.com/gweiermann/vue-ssr-postprocessing-cms).
Instead of changing the inner workings of the existing CMS, I wanted to add a transformation step after the CMS has generated the HTML and its other content.
So to be as little invasive as possible I added a reverse proxy to the existing infrastructure that serves as a middleware inbetween the CMS and the browser.
When a browser makes a request to my reverse proxy, it will fetch the response from the CMS and then transform the HTML using a Vue SSR pipeline and then send it back to the browser.

## The transformation step
To know how to build your own Server Side Rendering transformation, you first need to understand, how the concept works:
Info:
1. What is the server side rendered html? -> Laying in the DOM already.
2. How do I hydrate the app? -> Vue needs to know how the html looked like before it was rendered.
All of this is handled for you when you are using for example Nuxt. But because there doesn't exist a solution yet for our approach, we need to provide both ourselves.

To render the html its more simple than you think: Vue already provides a single function to render the html for you: `renderToString`.
It takes a Vue template string and it returns the rendered html as a string.
But how do we give context about how to hydrate?
That's also kind of simple: We just take the unrendered html and send it to the client as a string. Which is not as bad as you might think. In practice there was no big overhead in the size of the response.

## The implementation
Here's the heart of the transformation. Just call `ssr(cmsResponseHtml)` with the html that was received from the CMS. And you will get the whole transformed HTML document you need to send instead to the browser. It's that simple.
Keep in mind that this solution is just a proof of concept and was not yet used in production.

```typescript
// ssr/ssr.js
import createVueApp from '@/app.js'
import * as cheerio from 'cheerio'
import { renderToString } from 'vue/server-renderer'

export default async function ssr(html) {
    const $ = cheerio.load(html)
    const appContainer = $('#app')

    // create app
    const template = appContainer.html()
    const app = createVueApp(template)

    // render it
    const vueRender = await renderToString(app)

    // replace html of container with rendered html
    appContainer.html(vueRender)

    // pass the unrendered html to js
    const injectedTemplate = JSON.stringify(template)                                            // remove unnecessary whitespace
    $('head').append(`<script>
        window.SSR_TEMPLATE = ${injectedTemplate}
    </script>`)

    return $.html()
}
```

Here broken down:
```typescript
const $ = cheerio.load(html)
const appContainer = $('#app')
```
Will parse the html and grep the app container. Since we only want to tinker with the vue html and nothing else.  
Then we prepare the render. For that we need to create the vue app as we would have done it in the client side. But now we are on the server (make sure that your vue code doesn't access window or document here):
```typescript
const template = appContainer.html()
const app = createVueApp(template)
```

The function `createVueApp` is defined as follows:
```typescript
// src/app.js
import HelloWorld from "@/components/HelloWorld.vue";
import TheWelcome from "@/components/TheWelcome.vue";
import {createSSRApp} from "vue$";

export default function createVueApp(template) {
    return createSSRApp({
        template,
        components: {
            HelloWorld,
            TheWelcome
        }
    })
}
```
Where `HelloWorld` and `TheWelcome` are the components that are globally available for the CMS. `vue$` is the vue bundle for client side rendering which couldn't be eliminated unfortunately.
`template` is just the unrendered html in the app container.

Then we render the app:
```typescript
const vueRender = await renderToString(app)
```

This will return the rendered html as a string.
Then we replace the html of the app container with the rendered html:
```typescript
appContainer.html(vueRender)
```

But keep in mind that we also need to provide the unrendered html to the client. So we inject it into the head of the html:
```typescript
const injectedTemplate = JSON.stringify(template)  

$('head').append(`
    <script>
        window.SSR_TEMPLATE = ${injectedTemplate}
    </script>
`)
```
The unrendered html is now made available globally as `window.SSR_TEMPLATE`. Look at the trick to use `JSON.stringify` to perfectly escape the template string and inject it as javascript code.

To compile all of our changes to the html document we ask cheerio to return the html:
```typescript
return $.html()
```

The unrendered html `window.SSR_TEMPLATE` is used on the client side to hydrate the app:
```typescript
// src/main.js
import createVueApp from "@/app.js";

createVueApp(window.SSR_TEMPLATE).mount('#app')
```
Where `createVueApp` is the same function as on the server side.

In the file [ssr/server.js](https://github.com/gweiermann/vue-ssr-postprocessing/blob/main/ssr/server.js) you can see a very simple express server that works as the described middleware inbetween.

## Sending context to the ssr processing step from the vue app
The codebase I was working with had an approach to dynamically load css where the cms would insert this html element: `
```html
<cms-import href="/css/style.css" />
```
which would then render to 
```html
<div style="display: none;"></div>
```
And would add a css loading directive in the head at runtime.
```html
<link rel="stylesheet" href="/css/style.css" />
```

You could improve this by server side rendering the css loading directive directly.
It's easier than you think:
You can add a second parameter to `renderToString` to pass in a context object.
```typescript
const context = {
    cssSources: []
}
const vueRender = await renderToString(app, context)
// context is now enriched with the css sources (by the <css-import /> component)
// now you can add <link /> tags to the head of the html using context.cssSources
```
And the `<css-import />` component would enrich the context object with the css source url:
```
import { useSSRContext } from 'vue'

if (import.meta.env.SSR) {
  const ctx = useSSRContext()
  ctx.cssSources.push('/css/style.css')
}
```

## To look out for
The unrendered html needs to be html5 compliant. Using self closing tags for custom vue elements for example will crash the `renderToString` function.

## Summary
This approach is a simple way to add Server Side Rendering to a classical CMS. It's not a perfect solution and there are still some things to look out for. But it's a good starting point to improve the performance of your website. As mentioned before the approach was not used in production due to the client didn't want to change their infrastructure but I still wanted to share it with you since I thought this is a very interesting approach.
Here's the Github repository: [https://github.com/gweiermann/vue-ssr-postprocessing-cms](https://github.com/gweiermann/vue-ssr-postprocessing-cms)
